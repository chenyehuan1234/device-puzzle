# v0.5.2 · 2026-09-19 · 脚本编码一次性修好 + 关卡包「按内容认」

## 1. 这次要解决什么

- **脚本编码坑**：`.ps1` 存成「UTF-8 无 BOM」时，Windows PowerShell 5.1 会按 ANSI 解码 —— 中文变乱码、严重时直接语法错误，症状是双击 `build.cmd` 黑窗一闪而过、或者提示找不到「关卡库.json」。
- **自检读 dump 的编码坑**：`check-single.ps1` / `run-probe.ps1` 用 `Get-Content $dump -Raw` 读 Chrome 的 `--dump-dom` 输出，PowerShell 5.1 会按 ANSI 解码，于是脚本里所有**中文断言**（比如「主对角（左上↔右下）」）永远匹配不上 —— 自检结果不可信。
- **关卡包只认文件名**：打包脚本原本只找 `关卡库.json` / `levels.json`。你从编辑器导出成「我的关卡库.json」「关卡库 (1).json」就认不出来了。
- **不做**：不改任何游戏规则、不改关卡 JSON 格式、不改界面交互。

## 2. 改了什么

按「用户看得见的行为」写：

| 需求 | 结果 | 怎么验证的 |
| --- | --- | --- |
| 脚本编码不再坑人 | 三个 `.ps1`（`tools/build.ps1`、`tools/check-single.ps1`、`tests/run-probe.ps1`）统一存成 **UTF-8 带 BOM**；新增 `tools/fix-script-encoding.ps1`，改完脚本跑一条命令就自动修好（`.cmd` → CRLF、`.ps1` → BOM） | `tests/packaging.test.js` 新增断言：逐个检查 BOM 字节 `EF BB BF` |
| 自检的中文断言真的能匹配上 | 读 dump 改成 `[System.IO.File]::ReadAllText($dump, UTF8)`，不再走 `Get-Content -Raw` | 新增断言：`.ps1` 里必须出现 `ReadAllText($dump, [System.Text.Encoding]::UTF8)`；且「先读 dump 再删 dump」（这个顺序我犯过错，会直接报 FileNotFound） |
| 关卡包「文件名叫什么都行」 | 打包时先扫项目根目录（找不到再退到**上一级目录**）所有 `.json`，**按内容**判断是不是关卡包（认 `format: mp-level-bundle` + `chapters` + `levels`，手写没写 `format` 的也宽容接受） | 新增断言：造一个「名字起错了的」关卡包放根目录 → `findBundle` 能认出来；同时普通 json 和单个关卡文件**不会**被误认成关卡包 |
| 有多个关卡包时不再糊涂 | 优先级：先看习惯名字（`关卡库.json`）→ 再看哪个关卡多 → 最后看谁最新。用了哪个、**还有哪几个没用**，打包时都打出来提醒 | 新增断言：`findBundle` 找到标准名字的那个，并把名字不对的列进 `others` |
| 快把自检垃圾打进包里会被提醒 | 关卡包里若混着大关名含「探针 / 冒烟 / 测试关卡 / CtrlS」的测试大关，打包时给出 ⚠ 提示和处理办法 | 代码审查（`tools/build-single.js` 的 `junk` 判断） |
| 打包提示说人话 | 无关卡包时不再只甩一句「自己画关」，而是直接给三步操作路径；从上一级目录找到关卡包时也提示建议挪进来 | 手动跑 `build.cmd` 观察输出 |

## 4. 规则 / 交互变化

- **游戏规则：无变化。** 9 种设备判定、通关条件、关卡格式全部原样。
- **打包行为变化（以前 → 现在）**：
  - 以前：只认 `关卡库.json` / `levels.json` 两个文件名。
  - 现在：按**文件内容**认，文件名叫什么都行；根目录没有会去上一级目录找；多个候选会挑关卡最多的并提示其它候选。
- `findBundle()` 的返回值从「对象或 null」变成「始终是对象，用 `file === null` 表示没找到」，多了 `scanned` / `others` / `byName` / `dir` 字段。这是内部 API，只被 `build()` 和测试使用。
- ❓ 我自作主张的两处，请确认：
  - 关卡包识别**放宽**到「没写 `format` 也算」（手写包也能用），代价是理论上有个 JSON 恰好同时有 `chapters` 和 `levels` 就会被误认 —— 概率极低，但确实放宽了。
  - 上一级目录的扫描只做一层，不递归。

新增/修改的用例：

- `PowerShell 脚本的编码` 组：三个 `.ps1` 必须是 UTF-8 带 BOM；`check-single.ps1` 只读一次 dump 且「先读后删」；dump 必须按 UTF-8 读；`tools/fix-script-encoding.ps1` 必须存在且同时处理 `.cmd` 和 `.ps1`
- `关卡包识别（文件名叫什么都行）` 组：`findBundle` / `asBundle` 可单独调用；名字起错的关卡包能按内容认出；有标准名字时优先它并把其它列进 `others`；普通 json 与单个关卡文件不被误认
- 新增的文件在测试后会被清理（`__测试用的*.json`），不污染工作区

> 未跑 `tests/run-probe.ps1`（需要无头 Chrome）和 `build.cmd` 的自检环节。`tests/run-probe.ps1` 的改动只是换了个读取方式，逻辑未变。

## 6. 已知问题 / 取舍

- 关卡包「按内容识别」是启发式的，不是强类型校验 —— 判错的兜底是打包时会打印「这次看过的 json 清单 + 哪个是关卡包」，肉眼能发现。
- `tools/fix-script-encoding.ps1` 会遍历项目内所有 `.ps1` 并**重写**（加 BOM），不做内容校验。它只改编码不改内容，但仍然建议改完脚本再跑、并让 `packaging.test.js` 复核一遍。
- 编码问题**只在 Windows PowerShell 5.1 上才致命**，PowerShell 7 默认按 UTF-8 读。所以这个坑在 `pwsh` 下测不出来 —— 必须靠 `packaging.test.js` 的字节级断言兜住。
